# PART II. PRIMARY PRODUCT DESIGN

## 4. The central principle: REPORT FIRST, ADMINISTRATION SECOND

**This is the most important usability requirement in the entire project.**

The user does not want to operate Reunion like an excessively complicated management game.

The user does not want to manually update Parliament, the cabinet, the military, treasury, diplomatic relations, and the national timeline after every roleplay event.

Instead, RNAS must be designed around a natural-language reporting workflow.

### Primary workflow

**Write Report → Review Changes → Approve → Update Reunion**

Example report:

"October 7, 1992. President Donahue authorized the deployment of 4,000 troops to Dalmatia. Parliament passed a 2 billion RMC defense appropriation. Finance Minister Curro redirected 500 million RMC from existing programs to military infrastructure. Croatia condemned the military buildup."

RNAS should interpret this report and propose changes to:

- Historical timeline.
- Presidency.
- Military deployment records.
- Parliament.
- Treasury.
- Ministry budgets.
- Diplomatic relations.
- National event registry.

The user should not have to open each department manually.

The system should show a consolidated review:

**Proposed changes:**
- One presidential authorization.
- One military movement order.
- One parliamentary legislative action.
- One defense appropriation.
- One treasury reallocation.
- One diplomatic event.

**Unresolved information:**
- Which specific formations supply the 4,000 troops?
- Was the deployment merely ordered or confirmed completed?
- Which appropriations fund Curro's reallocation?

The user must be allowed to leave nonessential details unresolved.

The application should create explicit missing-information records rather than forcing immediate answers or inventing details.

### Critical distinction

Do not confuse an event being reported with an event being proposed.

For example:

"Parliament approved the appropriation" means an approval is being reported.

"Parliament is considering an appropriation" means no approval has yet occurred.

"The President orders a brigade to Dalmatia" means a movement has been ordered, not necessarily completed.

"The brigade arrived in Dalmatia" means the movement has been completed.

The difference must be represented in the database.

Allow the system to record a real event while retaining uncertainty about its details.

Do not maintain disconnected copies of parliamentary, military, economic, or diplomatic information.

Do not permit AI to execute arbitrary database writes.

## 9. Canon authority and contradictions

Build around an evidence-based canon model.

Every historical assertion must include:

- Subject.
- Relationship or property.
- Value.
- Source.
- Relevant date.
- Date precision.
- Approval status.
- Confidence.
- Supersession history.
- Conflicts.

Separate:

**Canon status:** Confirmed, provisional, disputed, superseded, rejected.

**Operational status:** Proposed, planned, ordered, contracted, delivered, completed, canceled, etc.

**Source confidence:** How strongly the evidence supports the assertion.

These concepts must not be combined into one status field.

### Canon Review Center

Create a functional review interface with three inboxes:

1. Contradictions.
2. Missing information.
3. Proposed additions or changes.

For contradictions, show competing claims and their original sources.

Allow the user to:

- Accept either source.
- Merge compatible details.
- Replace both with a corrected fact.
- Preserve both for different dates.
- Reject an incorrect assertion.
- Leave the issue unresolved.
- Reopen previously resolved issues.

For missing information:

- Allow exact dates.
- Approximate dates.
- Date ranges.
- Month or year only.
- Relative chronology.
- Explicit unknown values.
- Deferred decisions.

Avoid generating hundreds of low-value questions.

Prioritize issues that affect national continuity or multiple departments.

For example, uncertainty over a major war's end date matters more than a missing middle name.

# PART V. AI ASSISTANCE AND SIMULATION

## 18. Two separate user actions

RNAS must clearly distinguish:

### Record What Happened

The user describes an event that occurred in the roleplay.

The system extracts and records what the user reported.

It must not reinterpret the report as a hypothetical simulation.

### Simulate What Might Happen

The user requests a possible outcome.

Examples:

- How would Parliament vote on a proposed bill?
- How would cabinet ministers respond to a major budget deficit?
- What diplomatic response might Croatia make?
- What are the likely economic consequences of mobilization?
- How might an election unfold?
- How might a military crisis develop?

The simulation creates a scenario, not immediate canon.

The user may accept all, part, or none of the outcome.

## 19. Three simulation modes

### Manual mode

The user determines the result directly.

RNAS validates the administrative consequences and records the approved outcome.

### Assisted mode

The system proposes possible outcomes based on the available records, rules, and assumptions.

The user makes the final decision.

**This should be the default mode for significant political, diplomatic, military, and economic simulations.**

### Simulation mode

The system uses documented deterministic rules, seeded probabilities, and optional AI reasoning to generate hypothetical outcomes.

Simulations should be reproducible from a starting state, rules version, assumptions, and random seed.

Do not present predictions as established facts.

## 20. AI model integration

Build an optional, provider-independent AI layer.

Possible backends:

- OpenAI API.
- Locally hosted models through Ollama.
- Other compatible providers in the future.

The core application must work without an API key.

Budget calculations, record retrieval, vote arithmetic, historical snapshots, validations, and administrative actions must not require AI.

Use AI primarily for:

- Natural-language report interpretation.
- Entity matching where ambiguous.
- Historical document extraction.
- Political analysis.
- Parliamentary debate.
- Cabinet discussions.
- Diplomatic negotiations.
- Scenario generation.
- Narrative explanations.

### AI context

Never assume the AI model automatically knows Reunion's history.

For every task, retrieve the relevant approved canon and structured national state from the database.

Provide:

- Relevant historical period.
- Applicable institutions.
- Important people.
- Existing political positions.
- Financial data.
- Military resources.
- Active treaties.
- Prior events.
- Known uncertainties.

Avoid sending the entire database with every request.

Use targeted retrieval.

### AI safety and validation

- Store API keys securely on the server.
- Never commit keys to Git.
- Never expose keys in client-side code.
- Provide configurable spending limits and request logs.
- Validate structured AI outputs.
- Never allow arbitrary AI-generated SQL.
- Never allow the AI to bypass canon approval.
- Provide an AI-disabled mode.
- Handle provider errors without corrupting data.

## 21. National Decision Engine

Build a shared process for actions affecting multiple institutions.

Example:

"President Donahue proposes 5 billion RMC in military appropriations and orders national mobilization."
